# 이리로 — QR 기반 실내 AR 길안내

지하철역처럼 GPS가 안 되는 실내에서, 곳곳에 붙인 QR을 카메라로 비추면 현재 위치를 계산하고
가고 싶은 곳까지 바닥에 화살표를 띄워 안내하는 웹앱입니다. 앱 설치 없이 폰 브라우저에서 열립니다.

로봇이 기준 마커로 자기 위치를 잡는 방식을 그대로 가져왔습니다.

1. **QR로 위치 잡기**: 지도에는 각 QR의 위치·방향·크기가 적혀 있습니다. 영상에서 QR의 네 모서리를 찾고,
   폰의 기울기 센서 값을 더해 카메라의 위치와 방향을 계산합니다.
2. **걸음으로 이어 가기**: QR이 안 보이는 동안은 걸음 수와 폰이 향한 방향으로 위치를 이어 갑니다.
   다음 QR을 비추면 쌓인 오차가 다시 0에 가깝게 맞춰집니다. 그 사이에도 사람이 실제 모퉁이에서 꺾어
   다음 통로 방향으로 두 걸음을 걸으면, 추정 위치를 그 통로 위로 옮겨 걸음 수 오차를 모퉁이마다 지웁니다.
3. **복도를 보고 방향 맞추기**: 벽 QR 한 장으로 잡은 방향은 몇 도쯤 틀릴 수 있어서, 그대로 두면 화살표가
   복도와 비스듬하게 그려집니다. 그래서 카메라에 보이는 복도 선(바닥·천장과 벽의 경계)이 모이는 방향을 찾아
   추정 방향을 계속 바로잡습니다. 폰을 숙여 들어 복도 끝이 안 보여도 바닥과 벽의 경계선이 보이면 됩니다.
   복도 선이 안 보일 때는 통로의 곧은 구간을 걷는 방향으로 대신 맞춥니다 (사람마다 폰을 살짝 틀어 드는
   버릇은 복도 선으로 방향이 맞아 있는 동안 배워 둡니다).
4. **경로 찾기**: 통로 그래프에서 목적지까지 최단 경로를 구합니다.
5. **AR 안내**: 바닥 화살표, 꺾는 곳 표지판, 목적지 핀을 영상 위에 그리고 음성으로도 안내합니다
   (한국어·영어·일본어·중국어). 화살표는 통로의 어느 쪽으로 걷든 항상 발밑에서 시작하고,
   다음 모퉁이를 조금 지난 곳까지만 그립니다 (모퉁이 뒤쪽은 실제로는 벽에 가려 보이지 않으므로).

## 바로 실행

```bash
python3 serve.py
```

- 노트북: <http://localhost:8000/?sim=1> — **가상 역**에서 가상 보행자가 자동으로 걸어가며 전체 흐름을 보여 줍니다.
  실내 시연이나 발표에 쓰기 좋습니다.
- 폰: 실행하면 터미널에 `https://<노트북 IP>:8443/` 주소가 나옵니다. 노트북과 같은 와이파이(또는 폰 핫스팟)에
  연결한 뒤 그 주소를 엽니다. 임시 인증서라 경고가 뜨면 "계속 진행"을 누르고, 카메라와 "동작 및 방향" 권한을 허용하세요.

폰 브라우저는 https가 아니면 카메라와 센서를 막습니다. 여러 사람에게 보여 줄 때는 이 폴더를 그대로
정적 호스팅(GitHub Pages, Firebase Hosting 등)에 올리면 경고 없이 열립니다. 빌드 과정은 없습니다.

## 실제 폰으로 바로 확인하기 (인쇄 없이)

노트북 화면에 QR 한 장을 띄워 "벽에 붙은 안내판"으로 삼습니다.

1. 노트북에서 <http://localhost:8000/test.html> 을 엽니다.
2. 화면을 수직으로 세우고, 카드 한 장으로 크기를 맞추고, QR 중심의 높이를 적습니다.
3. 폰에서 `https://<노트북 IP>:8443/?map=desk&debug=1` 을 엽니다 (테스트 화면의 작은 QR을 찍어도 됩니다).
4. 목적지를 고르고 1m쯤 떨어져 큰 QR을 비춥니다. 화장실은 왼쪽 4m, 2호선 승강장은 오른쪽 4m,
   1번 출구는 뒤쪽 5m에 있다고 설정돼 있어서 화살표가 그 방향으로 나오면 정상입니다.

화면에 띄운 QR에는 크기와 높이가 함께 들어 있어서(`&s=100&h=90`) 지도 파일을 고칠 필요가 없습니다.

직접 만든 지도도 같은 방법으로 프린터 없이 시험할 수 있습니다. `test.html?map=<지도 이름>`을 열어
띄울 QR을 고르고, 그 화면을 지도 속 QR 자리의 벽에 붙여 세워 둡니다 (화면 하나에 QR 한 장).

## 내 공간에 설치하기

1. **지도 만들기**: <http://localhost:8000/editor.html> 에서 그립니다.
   - **통로**: 사람이 걷는 길의 가운데를 따라 차례로 누릅니다. 이미 그린 통로 위를 누르면 갈림길이 됩니다.
     통로 선이 다른 갈림점 위를 지나가거나 다른 선과 교차하면 그 자리에서 자동으로 이어집니다
     (이어지지 않으면 모퉁이에서 꺾지 못하고 선 끝까지 갔다 되돌아오는 경로가 나옵니다).
   - **목적지**: 종류(출구, 화장실, 승강장 등)를 고르고 통로 위의 위치를 누릅니다.
   - **QR**: 붙일 위치를 누르고 화살표로 방향을 맞춥니다. 벽 QR은 바라보는 방향, 바닥 QR은 인쇄면의 위쪽입니다.
   - 평면도나 안내도 사진이 있으면 배경으로 깔고 "축척 맞추기"로 실제 크기에 맞춘 뒤 따라 그립니다.
   - 길이는 줄자로 재거나, 바닥 타일 한 장의 크기에 장수를 곱해 구합니다.
   - 복도가 단순하면 오른쪽 "빠른 시작"에 모양과 길이만 적어 기본 지도를 만들 수 있습니다.
   - 아이폰 라이다로 스캔한 파일이 있으면 아래 방법으로 평면도를 자동으로 깔 수 있습니다.
2. **저장하고 미리 걸어 보기**: "저장"을 누르면 `maps/<파일 이름>.json`이 생깁니다.
   "가상 역에서 미리보기"로 그 지도 안을 가상 보행자가 걸어가는 것을 볼 수 있습니다.
3. **QR 인쇄**: "QR 인쇄"를 눌러 **실제 크기(100%)** 로 인쇄하고, 종이에 찍힌 10cm 선을 자로 확인합니다.
4. **붙이기**: 각 장의 오른쪽 아래 작은 지도에 붙일 자리가 빨간 동그라미로 표시돼 있습니다.
   벽용은 QR 중심 높이를, 바닥용은 화살표 방향을 맞춥니다. 실제로 붙인 자리가 지도와 다르면
   편집기에서 QR을 끌어 옮기고 다시 저장합니다.
5. **열기**: 폰에서 `https://<노트북 IP>:8443/?map=<파일 이름>` (저장하면 편집기 오른쪽에 주소와 QR이 나옵니다)

지도 저장은 `serve.py`가 처리하며, 이 노트북에서 `http://localhost`로 연 편집기의 요청만 받습니다.
같은 이름으로 다시 저장하면 이전 파일은 `maps/.backup/`에 남습니다.

### 아이폰 라이다로 평면도 만들기

라이다는 브라우저에서 쓸 수 없어서, 스캔은 라이다 스캔 앱으로 하고 그 결과 파일을 편집기가 읽습니다.

1. 라이다가 있는 아이폰(Pro 모델)에서 스캔 앱의 메시(공간) 스캔으로 그 층을 한 바퀴 돕니다.
   벽이 화면에 들어오게 천천히 걷습니다.
2. **OBJ**(또는 GLB)로 내보내 맥으로 보냅니다 (AirDrop). 압축 파일이면 풉니다.
3. 편집기에서 "LiDAR 스캔 가져오기"를 눌러 그 파일을 고릅니다.
   벽이 진한 선으로, 스캔된 바닥이 옅은 색으로 그려진 평면도가 **실제 크기 그대로** 깔립니다.
4. 실제와 좌우가 반대로 보이면 "좌우 뒤집기"를 누릅니다. 이 설정은 통로를 그리기 전에 맞춥니다.
5. 그 위에 통로, 목적지, QR을 찍습니다. 벽 QR은 스캔된 벽에 자동으로 붙고 통로 쪽을 바라보게 놓입니다.

저장하면 평면도 그림도 `maps/<파일 이름>.png`로 함께 저장되어 앱의 미니맵에 나오고,
가상 역에서는 스캔한 벽이 그대로 세워집니다.

읽을 수 있는 형식은 OBJ, GLB(압축되지 않은 것), PLY입니다. 이 기능은 만들어 낸 시험용 파일로만 확인했고
실제 스캔 앱이 내보낸 파일로는 아직 확인하지 못했습니다.

### 지도 형식

편집기가 만드는 파일의 형식입니다. 손으로 고쳐도 됩니다.

좌표는 도면 위에서 x가 오른쪽, y가 위쪽이고 단위는 미터입니다.
방향은 도면의 위쪽(+y)이 0도이고 시계 방향으로 커집니다 (오른쪽 90, 아래 180, 왼쪽 270).

```jsonc
{
  "id": "hallway",
  "markerSize": 0.16,                        // QR 한 변의 실제 길이 (m)
  "nodes": { "s": [0, 0], "j": [0, 10] },    // 통로 위의 점
  "edges": [["s", "j"]],                     // 걸어 다닐 수 있는 연결
  "markers": [
    // 벽 QR: facing은 QR이 바라보는 방향(벽에서 통로 쪽), h는 QR 중심 높이
    { "id": "W1", "mount": "wall", "x": -1, "y": 5, "h": 1.5, "facing": 90 },
    // 바닥 QR: facing은 인쇄된 QR의 위쪽이 향하는 방향
    { "id": "F1", "mount": "floor", "x": 0, "y": 1.5, "facing": 0 }
  ],
  "pois": [
    // type: exit, platform, toilet, elevator, ticket, locker, info, store
    { "id": "exit1", "type": "exit", "number": 1, "node": "s" },
    { "id": "toilet", "type": "toilet", "node": "j" }
  ],
  "walls": [[-1, -1, -1, 9]],                // 미니맵과 가상 역에 그릴 벽 (x1, y1, x2, y2)
  "start": { "x": 0, "y": 0.2, "heading": 0, "pitch": -40 }   // 가상 역 출발 위치
}
```

목적지 이름은 종류별 기본 이름이 4개 언어로 들어 있고, `name`·`detail`·`keywords`로 덮어쓸 수 있습니다
(`maps/station.json`의 2호선 승강장 참고).

### QR 배치 요령

가상 역에서 잰 값입니다 (가상 카메라는 1080p급). 실제 폰에서는 다를 수 있습니다.

| 배치 | 위치 오차 | 방향 오차 | 인식 거리 |
|---|---|---|---|
| 바닥 QR | 2cm 이내 | 0.3도 이내 | 약 2m |
| 벽 QR, 15도 이상 비스듬히 | 6cm 이내 | 1.5도 이내 | 약 3m |
| 벽 QR, 정면 | 최대 약 20cm | 최대 약 5도 | 약 3m |

- **갈림길에는 바닥 QR**이 좋습니다. 바닥 QR은 놓인 방향이 그대로 보여서 방향이 정확합니다.
- 벽에 붙은 작은 QR은 정면에서 보면 좌우 방향을 가리기 어렵습니다. 같은 벽에 1m쯤 띄워 두 장을 붙이면
  함께 보일 때 방향이 훨씬 정확해집니다.
- QR 사이 간격은 10m 안팎을 권합니다. 걸음 추정은 10m에 1m쯤 틀릴 수 있습니다.
- **모퉁이에서는 걸어오는 방향에서 정면으로 보이는 벽**(복도 끝의 막다른 벽)에 붙이는 것이 좋습니다.
  옆벽에 붙이면 멈춰 서서 몸을 돌려야 찍히지만, 정면 벽에 붙이면 걸어가는 동안 저절로 찍혀서
  꺾기 직전의 위치가 정확해집니다.
- 벽 QR의 **중심 높이**(지도의 `h`, 기본 1.5m)를 실제와 같게 적어야 합니다. 높이가 틀리면 카메라 높이가
  틀리게 계산돼서 바닥 화살표가 실제보다 가깝거나 멀게 보입니다 (`?debug=1`의 `h` 값이 폰을 든 높이와 비슷해야 정상).

## 주소 옵션

| 옵션 | 뜻 |
|---|---|
| `?map=station` | 사용할 지도 (`maps/<이름>.json`) |
| `?sim=1` | 가상 역 모드 |
| `?dest=toilet` | 목적지를 정하고 바로 안내 화면으로 (시연용) |
| `?lang=en` | 언어 고정 (`ko`, `en`, `ja`, `zh`) |
| `?debug=1` | 추정 위치, 오차, 걸음 수 표시 |
| `?fov=65` | 카메라 긴 변 화각 가정값. `debug`에 나오는 QR까지 거리가 실제보다 길면 키웁니다 |
| `?stride=0.65` | 보폭(m). 적지 않으면 QR 두 개 사이를 걸을 때마다 자동으로 맞춰지고 기기에 기억됩니다 |
| `?stepth=0.9` | 걸음 감지 민감도. 걸음이 안 세어지면 낮춥니다 |
| `?slam=1` | 카메라 움직임 추적(SLAM)으로 QR 사이의 이동을 잽니다 (걸음 수 대신). 아래 "카메라 움직임 추적" 참고 |
| `?slamdrop=20-26` | (가상 역, `slam=1`과 함께) 그 시간(초) 동안 추적을 놓친 것으로 흉내 냅니다. 여러 구간은 쉼표로 |
| `?vp=0` | 카메라의 복도 선으로 방향을 맞추는 기능 끄기 (비교용) |
| `?walkyaw=0` | 걸은 방향으로 방향을 맞추는 대비책 끄기 (비교용) |
| `?turnsnap=0` | 모퉁이를 돈 순간 위치를 다음 통로에 맞추는 기능 끄기 (비교용) |
| `?walker=truth` | (가상 역) 자동 보행자가 앱의 화살표가 아니라 실제 통로를 따라 걷습니다. 화살표가 실제와 얼마나 어긋나는지 잴 때 씁니다 |
| `?hold=5` | (가상 역, `walker=truth`와 함께) 폰을 걷는 방향에서 오른쪽으로 5도 틀어 들고 걷는 사람을 흉내 냅니다 |

`?debug=1`에서는 영상에서 찾은 복도 방향이 노란 점선으로 그려집니다. 이 선이 실제 복도와 나란하면 방향 찾기가
맞게 되고 있는 것이고, 글자 줄의 `corridor off`가 0에 가까우면 화살표도 그 방향에 맞춰져 있는 것입니다.
| `?m=A1` | QR을 폰 기본 카메라로 찍어 들어올 때 붙는 마커 ID |

화면에 띄운 QR처럼 지도를 고치지 않고 시험할 때는 QR 주소에 `&s=<한 변 mm>&h=<중심 높이 cm>`를 붙이면 지도의 값 대신 쓰입니다.

## 카메라 움직임 추적 (`?slam=1`, 시험 기능)

기본 방식은 QR이 안 보이는 동안 걸음 수로 위치를 이어 가는데, 보폭과 걸음 감지의 오차 때문에 10m에 1m쯤 틀릴 수 있습니다.
`?slam=1`을 붙이면 8th Wall 엔진(SLAM)이 카메라 영상의 특징점을 따라가며 잰 **실제 이동량**으로 대신 이어 갑니다.

- 엔진에서는 이동량만 가져다 씁니다. 폰의 자세와 방향 맞추기(QR, 복도 선)는 기본 방식과 같습니다.
- 엔진의 좌표계는 지도와 무관해서 기울기 센서와 비교해 방향을 맞춥니다 (`js/tracker.js`).
- 엔진의 길이 단위는 미터가 아닙니다 (실제 폰에서 1단위가 0.7~0.9m쯤이었고 실행할 때마다 다릅니다). 그래서
  처음에는 QR로 잰 카메라 높이로 어림하고, 걸음 수로 잰 거리와 견주어 크게 다르면 바로잡고(네 걸음 만에),
  QR 사이를 이동한 거리로 정밀하게 맞춥니다 (`js/main.js`의 `voOnFix`, `compareWithSteps`).
- QR의 위치를 계산할 때는 엔진이 그 화면과 짝지어 준 자세를 씁니다. 엔진을 거친 화면은 센서 값보다 0.1초쯤
  늦어서, 지금의 센서 값을 쓰면 손이 조금만 움직여도 계산이 어긋나 위치를 못 잡습니다.
- 엔진이 추적을 놓치면(특징 없는 벽을 가까이서 볼 때 등) 그동안은 걸음 수로 이어 가고, 다시 잡으면 돌아옵니다.
  엔진을 켜지 못하거나 오류가 나면 기본 방식으로 안내합니다.
- 화면 왼쪽 위 상태 표시가 "카메라로 추적 중"이면 엔진의 이동량을 쓰고 있는 것이고, "걸음으로 추정 중"이면 놓친 상태입니다.
  `?debug=1`에서는 `slam` 으로 시작하는 줄에 엔진 상태, 맞춘 단위(`scale`), 오류 내용이 나옵니다.

**검증 상태**: 계산 로직은 가상 역에서 엔진을 흉내 낸 추적기(임의의 방향·원점·단위, 잡음, 놓쳤다 다시 잡기)로 확인했고
(직접 만든 지도 두 개에서 화면에 쓰는 위치의 오차가 평균 0.6~0.8m → 0.2~0.3m, 중간에 두 번 놓치게 하면 0.35~0.45m),
엔진과 연결하는 부분은 문서대로 동작하는 가짜 엔진으로 확인했습니다.
실제 폰(아이폰, iOS용 크롬)에서는 2026-11-20에 엔진이 켜지고 추적되는 것까지 기록(`diag/client.log`)으로 확인했습니다
(열 번 모두 시작, 상태 보고의 95%가 "정상", 엔진과 센서의 기울기 차이 0~5도). 그 기록에서 엔진의 높이 값이 걷는 동안
흘러가는 것과 QR이 보이는데 위치를 못 잡는 경우를 발견해 위와 같이 고쳤는데, **고친 뒤의 정확도는 실제 폰에서 아직 재지 못했습니다.**

엔진은 화질이 낮은 카메라 영상을 쓸 수 있어서, 이 모드에서는 QR을 기본 방식보다 가까이에서 비춰야 할 수 있습니다.

### 폰에서 무슨 일이 있었는지 보기

폰에서는 오류 내용을 보기 어려워서, `?debug=1`이나 `?slam=1`로 열면 앱이 진행 상황과 오류를 노트북의 `serve.py`로 보내
`diag/client.log`에 한 줄씩 남깁니다 (엔진 시작 단계, 실패 사유, 5초마다의 추적 상태, 스크립트 오류).
이 기록은 이 서버가 내보낸 페이지에서 보낸 짧은 JSON만 받고, 파일이 2MB를 넘으면 이전 것을 `client.log.1`로 넘깁니다.
엔진을 켜지 못했을 때는 화면 안내 문구 아래 괄호 안에도 이유가 나옵니다 (`?debug=1`일 때).

## 한계

- **실제 폰 시험은 한 건물의 복도에서만 했습니다.** 계산과 화면은 주로 가상 역과 가짜 카메라 영상으로 확인했고,
  아래 수치도 가상 역에서 잰 것입니다.
- QR이 안 보이는 구간은 걸음 수로 추정하므로, 화살표가 꺾이는 자리가 실제 모퉁이와 수십 cm에서 1m쯤
  어긋나 보일 수 있습니다 (보폭이 맞춰지기 전인 첫 구간이 가장 큽니다). 카메라 영상으로 움직임을 직접 추적하는
  방식(ARKit, SLAM)을 쓰지 않는 한 남는 한계입니다.
- 브라우저가 카메라 초점거리를 알려 주지 않아 화각을 가정합니다. 기기에 따라 거리가 10% 안팎 틀릴 수 있어
  `?fov=`로 맞춥니다.
- 걸음 추정은 폰을 앞으로 들고 걷는다고 가정합니다. QR을 자주 비출수록 정확합니다.
- 복도 선으로 방향을 맞추는 기능은 기울기가 다른 곧은 선이 둘 이상(예: 양쪽 벽의 바닥 경계) 보일 때만 작동합니다.
  실제 복도 사진 15장으로 만든 시험에서 폰을 10~25도 숙였을 때는 90% 안팎, 40도 숙였을 때는 절반쯤에서
  방향을 찾았고(찾은 경우의 오차는 평균 0.4~0.7도), 50도 넘게 숙이면 거의 못 찾습니다. 넓은 홀이나 벽을 마주 볼 때,
  바닥에 불빛이 심하게 비칠 때도 못 찾으며, 그때는 걸은 방향으로 맞추는 대비책(2~3도 수준)이 대신합니다.
- 한 층만 다룹니다. 계단·에스컬레이터로 층이 바뀌는 경우는 지도 형식을 넓혀야 합니다.
- 목적지 찾기는 검색어 사전 방식입니다. LLM을 붙이려면 `js/destinations.js`의 `matchDestination`만 바꾸면 됩니다.
